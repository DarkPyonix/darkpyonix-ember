Agents

Agents

Ember runs each agent's own, unmodified CLI on the main server, through that agent's own non-interactive protocol. Your agent settings, models and session IDs keep working as they do natively. Ember adds what one CLI on one laptop cannot do: many accounts, shared MCP servers, schedules, and agents that message each other.

The server detects the installed agents and their versions at start and on demand (GET /api/v1/agents); a missing agent is shown as not installed, not as an error. Each agent's binary can be set with EMBER_CLAUDE_BIN, EMBER_CODEX_BIN, EMBER_AGY_BIN and EMBER_OMP_BIN; otherwise the name is looked up on PATH.

An idle session releases its agent process after EMBER_IDLE_SECS (300 by default). The next message starts it again through the agent's own resume, so the conversation continues where it was. REST paths on this page are shown as the code serves them today; #63 changes /api/v1/... to /api/....

Claude Code Implemented

  • Approvals. Each permission prompt becomes an approval card: allow once, always allow, or deny. "Always allow" covers that tool for the life of the process; later requests for it are answered at once, and the tool call still shows in the conversation.
  • Interrupt and resume. Interrupt ends the turn cleanly. A released or restarted session comes back with --resume.
  • Accounts. Each account is its own CLAUDE_CONFIG_DIR, see Accounts.
  • Other computers. Shell commands run on the session's computer through the ember-exec shim. File tools see the computer's project through a mount at the same path (EMBER_MOUNT: auto, nfs, fuse or off; the server must be built with the mount-nfs or mount-fuse feature).

The adapter was checked against Claude Code 2.1.288 and a recorded real session.

Codex Implemented

Ember runs codex app-server and speaks its JSON-RPC over stdio. A thread id is the session id, so Codex's own resume works.

  • Messages mid-turn. A message sent while Codex is working is added to the running turn with turn/steer, as Codex's own clients do.
  • Approvals. Command, file-change and permission requests become approval cards.
  • Settings. Codex's own approval policy, sandbox, model and config.toml apply as they do natively.
  • Other computers. Ember registers the computer with Codex's experimental environment/add so Codex runs its tools there. That a real turn's shell and patches run remotely is not verified yet.

The protocol was read from codex-cli 0.155.1 and checked against a captured real session.

Sign in with ChatGPT Partial

A self-hosted ember server can sign in with your ChatGPT account, so that your ChatGPT Plus or Pro plan can be used in addition to Codex token usage. OpenAI allows this only for open-source, locally hosted apps, so it is off when EMBER_HOSTED=1 and never offered through darkpyonix.dev.

  1. POST /api/v1/chatgpt/signin returns the authorization URL. Open it in a browser.
  2. OpenAI redirects to http://127.0.0.1:<port>/auth/callback on the server (EMBER_CHATGPT_REDIRECT_PORT, default the server's port).
  3. If your browser runs on another machine, that address does not reach the server: paste the final URL into POST /api/v1/chatgpt/signin/complete.

Tokens are stored encrypted and never returned by the API. The weekly cap is set by you in ChatGPT's settings, and no API reports it. Sign-in and token handling are implemented; using the plan from a session, and showing the cap, are not done yet (#16).

Antigravity Partial

Antigravity's print mode cannot ask for permission: it silently refuses any tool that needs one. So Ember runs it without its own prompts and makes its own PreToolUse hook the only gate. The hook lives in a private folder per session, under <data dir>/agy/; nothing is written to ~/.gemini or to your project, so your own agy sessions are unaffected.

  • Every tool call goes through the hook. Read-only tools inside the workspace pass; anything else becomes an approval card.
  • The hook answers only allow or deny. Any error (server unreachable, unknown token, odd reply) becomes deny.
  • An unanswered card is denied after 58 minutes, before agy's own hook timeout, with an "Approval for tool timed out; retry." notice.
  • Before every turn Ember checks that agy has loaded the hook. If not, the turn is refused.
  • Each run has a fresh token, revoked when it ends. Ending or interrupting a turn denies every pending card.

Version pin. These rules were tested on agy 1.2.16, which is pinned. Another version gets a notice and runs read-only: only read-only tools inside the workspace, everything else denied without asking. The pin moves only after the tests pass on the new version.

Sandbox. --sandbox is on (EMBER_AGY_SANDBOX=0 turns it off). Under it, on 1.2.16, shell commands cannot write even inside the project, while the file-edit tools can. The cause is being investigated in #65.

Not supported yet: accounts (agy keeps its login in ~/.gemini and has no variable to move it), sessions on another computer, and steering a running turn.

OMP and other ACP agents Partial

Agents that speak the Agent Client Protocol (ACP, version 1) run through one generic adapter. They are configured, not compiled in, with EMBER_ACP_AGENTS (JSON) or EMBER_ACP_AGENTS_FILE (the same JSON in a file):

A string is a preset. The preset omp runs omp acp. An object needs name and command and may add args, model_args, instructions_args, version_args and env. Each agent appears as an agent kind under its configured name.

  • Permission requests become approval cards (allow once, always allow, deny).
  • File reads and writes and terminal commands that the agent sends through ACP run on the session's computer, through its ember node.
  • ACP has no steering, so a message sent mid-turn is queued for the next turn.
  • No account isolation yet: log in with the agent's own CLI on the server.

The adapter is tested against a fake ACP agent. It has not yet been run against a real OMP, because OMP is not installed on the test server (#53).

Accounts and usage routing Implemented

The main server can hold several accounts per agent for Claude Code and Codex. Each account is a directory, <data dir>/accounts/<id>, that the CLI is pointed at through its own variable: CLAUDE_CONFIG_DIR or CODEX_HOME. Credentials, settings and native session files then stay apart, without patching either CLI.

  1. Create an account: POST /api/v1/accounts with {"agent": "claude-code", "label": "work"}.
  2. The answer includes the exact login command, for example CLAUDE_CONFIG_DIR=<dir> claude auth login. Run it on the server as the user ember runs as. Ember never automates login. For Codex on a headless server, add --device-auth.
  3. POST /api/v1/accounts/{id}/check runs the agent's read-only status command.

A new session uses the account you choose. Otherwise the router picks, among accounts that are neither rate-limited nor logged out, the one with the fewest tokens used today (UTC), then the default account, then the oldest. The choice and its reason are stored on the session and do not change silently. A rate-limited account is skipped until its reset time; a completed turn on it clears the mark. GET /api/v1/accounts/route?agent=… shows what the router would choose now, and GET /api/v1/usage?days=7 shows tokens per account per day.

Keys in the server's environment

ANTHROPIC_API_KEY, OPENAI_API_KEY or CODEX_API_KEY in the server's own environment reach every agent process and override the account's login. The server warns about them at start.

API-key providers (any OpenAI-compatible or vendor API) are added with POST /api/v1/providers. Keys are encrypted at rest and never returned.

The central MCP registry Implemented

Add an MCP server once, and every agent session that supports MCP gets it when its process starts: Claude Code through --mcp-config, Codex through -c mcp_servers.<name> overrides, Antigravity through its session folder, and ACP agents in session/new.

  • Environment values are treated as secrets: encrypted at rest, never returned (only their names), never on a command line, never logged.
  • PATCH with "enabled": false switches a server off without deleting it.
  • Changes apply from each agent process's next start.

Scheduled prompts Implemented

A schedule sends a prompt on a cron expression in a time zone, at a fixed interval, or once. Each run either continues an existing session or starts a new one in the project. The prompt arrives like a user message, behind a [ember schedule] header line.

  • A trigger missed while the server was down is not silently run. It is recorded as missed, with a notice. With catch_up, only the latest missed trigger runs.
  • Cron times follow the time zone across daylight-saving changes; an hour that occurs twice fires once.

A2A messages Implemented

Sessions can message each other across vendors, computers and accounts. Every agent process gets EMBER_URL, EMBER_SESSION_ID and a per-session EMBER_RUNTIME_TOKEN, plus instructions for the ember-a2a command. No agent is modified.

  • A message enters the target like a user message, behind an [ember a2a] header that names the sender and gives a reply reference.
  • A busy target gets it at the next turn boundary. A sleeping target is woken. Undelivered messages survive a server restart.
  • Loop protection: at most 20 messages per session and 10 per pair of sessions within 10 minutes. Two agents told to reply to each other forever are stopped, with a notice.
  • A2A can be switched off for the whole server (EMBER_A2A=0, or PUT /api/v1/a2a/settings) or per session (/api/v1/sessions/{id}/a2a). Sends to or from a switched-off session are refused with a reason.

Teams and @@mentions Implemented

A session can lead a team. The first team spawn makes the calling session the leader; each teammate is a new session in the same project, with the agent, account and computer the leader chose. Teammates answer their own approvals in their own sessions.

  • At most 8 active teammates. A session belongs to at most one team, and teams do not nest.
  • Only the leader spawns and ends. Any member adds tasks; a teammate updates only its own or unassigned tasks.
  • An active teammate can message only its own team, and only its team can message it.
  • The conversation view shows a team panel with members, live status and the task list.

In the composer, @@ mentions another session: @@<id>, @@<title> or @@"<title with spaces>". Typing @@ shows matching sessions. Your message stays in this conversation unchanged, and each mentioned session gets a copy as an A2A message from this session, so it can answer here with one call. A mention you could not resolve loses nothing. Not yet verified: a team of real Claude Code and Codex sessions on different computers and accounts.
