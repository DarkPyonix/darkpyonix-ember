Remote browser

Remote browser

Ember can run a browser whose traffic leaves from one of your computers, so pages see that computer's IP address and its local network. The cookies, logins and history stay on the main server, so switching computers keeps the same logged-in browser. Agents can drive the same browser while you watch.

Where this stands

Partial The server side is implemented and tested piece by piece: the browser, its profile, egress through a computer, the view stream and the agent relay. Egress has not yet been run with a real Chrome through a real node, and the Ember client has no browser view yet. Track it in #12.

One browser per project

Each project gets one headless Chromium on the main server, with a 1280×800 viewport. It starts the first time something opens or views it.

  • The browser binary is EMBER_CHROME_BIN. Unset, the server looks for Google Chrome, Chromium or Chrome for Testing, then google-chrome or chromium on PATH, then the newest Chromium in the Playwright cache. With none found, the server starts without the remote browser and says so in its log.
  • EMBER_BROWSER_HEADFUL=1 shows a real window, for debugging.

REST paths below are shown as the code serves them today. Issue #63 drops the version, so /api/v1/... becomes /api/....

Where traffic leaves

Egress is chosen per project, and there are three kinds:

direct
The main server's own network.
proxy
A proxy URL: socks5://, socks4://, http:// or https://, without credentials.
computer
A registered computer. Traffic leaves through that computer's ember node. local means direct.

Switching egress restarts Chrome on the same profile, after closing it gracefully so cookies are written, so your logins survive the switch. The choice is stored in the server database and applied again after a server restart.

For a computer, the path is a chain. Chrome uses a SOCKS5 proxy on the main server's loopback; the main server copies those bytes, one WebSocket per connection, to the node's /v1/egress; the node opens the real connection.

  • Host names are resolved on the computer, so its local DNS names work.
  • Loopback goes through the proxy too, so localhost in the browser is the computer's localhost. A dev server running there is reachable.
  • If the computer cannot be reached, starting the browser fails. It never falls back to direct, because that would quietly show the main server's IP instead.
  • A computer that some project's browser uses cannot be removed (409).

On the computer, ember node allows every destination by default, because its localhost and LAN must be reachable. To narrow it, set EMBER_NODE_EGRESS_DENY, for example private,link-local,loopback or CIDR ranges. EMBER_NODE_EGRESS=off refuses egress entirely.

Agents in the browser Partial

Agents run on the main server next to the browser, so they reach it through a DevTools relay at /api/v1/browsers/{project}/cdp. Ember gives them an unmodified, off-the-shelf DevTools MCP server pointed at that relay. This is off by default; turn it on on the server:

With it on, every agent session starts with an MCP server named ember-browser for its project's browser:

  • chrome-devtools runs npx -y chrome-devtools-mcp@latest --wsEndpoint=<relay>.
  • playwright runs npx -y @playwright/mcp@latest --cdp-endpoint=<relay>.
  • Claude Code receives it through --mcp-config, Codex through -c mcp_servers.ember-browser.* overrides, Antigravity through the mcp_config.json in its session folder, and ACP agents in session/new. Your own MCP servers stay.
  • Without npx or bunx on the server, the setting is ignored with a warning.

The first run downloads the package, so Ember raises the MCP start-up timeout to 90 seconds. GET /api/v1/browsers/{project}/agent-config returns the same configuration if you want to wire an agent by hand. An egress switch closes the relay connections; the MCP server reconnects on its next tool call. Antigravity's own browser tools have not been tested with Ember.

Viewing and taking over

The browser is shown to you as a picture, not as a web page inside the client, because the launcher and conversation screens must never contain a webview. A viewer connects to GET /api/v1/browsers/{project}/view, a WebSocket that carries JPEG frames out and mouse, keyboard and navigation input in. Frames are sent only while someone watches, and all viewers share one stream.

  • While an agent sends commands, the state shows agent_active (for 3 seconds after its last command), so a viewer can show that the agent is working.
  • You can take over, for example to type a password. While you hold it, the agent's commands wait; when you release it, the agent continues where it was.
  • The Ember client has no browser view yet (#12). Phones can use the same stream, but touch is mapped to mouse input for now and every viewer shares the one 1280×800 viewport.

Things to know

  • The browser's raw DevTools port is open without authentication on the main server's loopback. Agents should use the relay.
  • The SOCKS5 listener for a computer is also unauthenticated on loopback, so any local process on the main server can use that computer's egress while the listener runs.
  • Ember's own API has no authentication yet. Keep the server on a trusted network.
  • For a Codex session working on another computer, whether Codex starts the MCP server where the relay is reachable is not verified.
