Computers and the hub

Putting a session to work on another computer

A computer joins Ember by running ember-node and being registered with the main server. There are three ways to register it: by its HTTP address, by its peer address, or by picking it from your darkpyonix.dev account. After that, any session can move onto it.

The API, for now

The client lists computers, assigns them to projects and switches sessions between them, but it cannot add a computer yet. Adding one goes through ember-server's HTTP API, run on the main server with curl. The routes live under /api and carry no version.

By HTTP address

The simplest way, for a computer on a network you trust. On the computer, start the node on an address the main server can reach:

Then register it on the main server:

The token is never returned by the API. EMBER_NODE_ROOTS limits the folders the node may touch, so a session cannot read or run anything outside them on that computer.

By peer address

Over the peer-to-peer transport, the node needs no open port, and both sides are authenticated by their keys. Each side prints its identity when it starts with the transport on.

  1. Start the main server with EMBER_TRANSPORT=1. It prints ember server peer id: … and ember server peer addr: ….
  2. On the computer, add that server peer id to the node's allow-list, then start the node with the transport. Without an entry it warns no allowed peers: every transport connection will be refused. A running node reloads allowed-peers on SIGHUP and disconnects peers that were removed from it.
  3. Register the node with its peer id, or with the whole peer addr object it printed, which also carries address hints:

The node token is still required on this path, as a second factor beside the key. Partial The transport is tested on an in-memory network; its measurement across real networks (home, office, LTE, symmetric NAT) is pending (#10).

Through the darkpyonix.dev hub

Partial The hub lets every device join your GitHub account with a one-time code. Each device then publishes its address there and finds the others there, so nobody types an address. Ember's side is tested against a fake hub but has not yet run against the live one, and the hub is moving from https://darkpyonix.dev to its own subdomain, still being decided (#62). Until that lands, the built-in default is the old address, so set EMBER_HUB_URL to the hub's address on the server and on every node.

1. Link the main server

The hub needs the transport, so the server runs with EMBER_TRANSPORT=1.

Open verification_uri_complete in a browser signed in to darkpyonix.dev with GitHub, and approve. A main server must be approved in the browser. GET /api/hub shows the registration afterwards. If the server restarts while the link waits, it resumes the same link.

2. Register each computer

Approve it in the browser, or let the main server approve it, since a computer's link may be approved by the account's main server:

The registration is saved in ~/.ember/node/hub.json. Restart the node with EMBER_NODE_TRANSPORT=1, or send it SIGHUP, so it publishes its address through the hub. To let in your account's main servers without editing allowed-peers, also set EMBER_NODE_HUB_ALLOW_SERVERS=1. ember-node hub status shows the state at any time.

3. Add it as a computer

The node token is still needed, because the hub never carries it. The computer is stored by its peer id alone, and the server resolves its address through the hub's directory.

Assigning computers to projects

The launcher lists computers at the bottom with their reachability ("Online", "Offline", or "Checking…" while it is not yet known) and the projects each serves. With a project selected, each computer has a switch, "Assign to project". A project can have many computers and a computer many projects. The API equivalent is PUT /api/projects/{name}/computers/{computer_id}, and DELETE on the same path to unassign.

Switching a session's computer

In a conversation, the header reads "On computer". Click it and pick another computer. The switch is refused while a turn is running or waiting for approval, because the running tool calls belong to the old computer; answer or stop the turn first. It is also refused when the target does not answer.

After a switch the client says "Switched to name. The agent is told with your next message." The agent's environment description (operating system, shell, toolchains) is replaced, not appended, and a notice tells it to re-read files and re-run commands before relying on them. How each agent's tools reach the computer:

AgentOn another computer
CodexEvery tool runs on the node through codex exec-server, so Codex must be installed on that computer too.
Claude CodeBash runs on the node through ember-exec. Read, Edit, Write, Glob and Grep work on the main server's disk, where the project mount puts the node's folder.
OMP and other ACP agentsFile reads, writes and terminals that the agent asks Ember for run on the node.
AntigravityNot supported yet: "Antigravity sessions cannot run on another computer yet".

Partial Codex and Claude Code's Bash tool were verified with a node registered as a separate computer on the same Mac. A switch between two physically separate computers is not verified yet (#6).

The project mount

Partial Claude Code's file tools run inside claude on the main server. So when its session is on another computer, Ember mounts that computer's project folder on the main server at the same absolute path. The tools then see the right files, and paths in the transcript stay true. The mount is written but not yet run on a real Mac mini or Raspberry Pi (#6).

  • Build: --features mount-nfs on a macOS main server, --features mount-fuse on Linux (Install). EMBER_MOUNT=off turns it off.
  • Mount point: the path must be creatable by the server's user. When it is not (another user's home, /home on macOS, a new top-level folder), run ember/server/scripts/ember-mount-setup.sh <path> once; it prints each sudo command before running it, and --dry-run only prints them.
  • Existing folders: a non-empty local folder at the same path is not mounted over, unless EMBER_MOUNT_SHADOW=1.
  • Scope: only the session's folder is mounted. Nested project folders, and the same path served from two computers, are refused.
  • Freshness: writes go to the node at once; changes made on the node by other programs show within about a second (EMBER_MOUNT_TTL_MS, default 1000).
  • Outages: every node call has a 4-second deadline, so a lost computer shows up as an I/O error instead of a hang.

Removing a computer

DELETE /api/computers/{id} removes a computer and its project assignments. It is refused while a session is on that computer, or while a project's remote browser goes out through it; move those first. To leave the hub, run ember-node hub forget on a computer, or DELETE /api/hub/registration on the main server. Add --local or ?local=1 to forget the registration here only, while the device stays in the account.
