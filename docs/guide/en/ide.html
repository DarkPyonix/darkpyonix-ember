Opening an IDE

Opening an IDE

A conversation is where you work with an agent. When you want to read or edit the code yourself, the Open IDE button at the top right of the conversation opens the session's project in an IDE. There are three choices, and they are three different programs, not three skins of one.

Where this stands

VS Code Web and JetBrains Gateway open today, from computers you describe in the server's configuration. Ember's own editor is planned (#32): choosing it shows a placeholder. The IDE does not yet follow the session's current computer by itself, see Which computer opens.

Three choices

ChoiceWhat opensStatus
Ember IDEEmber's own editor, drawn natively by dioxus-compose. No webview and no JavaScript engine.Planned #32
VS CodeVS Code Web running on the computer, wrapped by Ember's proxy, opened in your default browser.Partial
JetBrains GatewayA jetbrains-gateway:// link that starts the Gateway installed on your machine and connects to the computer over SSH.Partial

VS Code and Gateway are marked partial for the same reason: they open, but the computer they open on comes from a configuration list, not from the session. Gateway has also not been run against a real Gateway installation yet; only the link it builds is tested.

What the button does

The client asks the main server how to open each IDE for this session. The server only returns data and never opens a window itself, because the launcher process must never create a webview.

The answer lists three targets, always in the order ember, vscode, gateway. Each has available, and a reason when it is not available, for example "no ide_url configured for computer". The client shows that reason instead of failing silently.

  • The client remembers the target you chose last and lists it first next time.
  • It hands a URL to your operating system only if the scheme fits the target: http or https for VS Code, jetbrains-gateway:// or jetbrains:// for Gateway. So a server answer cannot make the client open a local file or program.
  • The folder that opens is the session's working directory, read as a path on that computer.

REST paths on this page are shown as the code serves them today. Issue #63 drops the version, so /api/v1/... becomes /api/....

Which computer opens Partial

Sessions already have a current computer, but the IDE targets do not read it yet. Until they do, the server takes each computer's IDE details from EMBER_IDE_COMPUTERS, and opens the default computer unless the request names another with ?computer=. The value is inline JSON or a path to a JSON file.

ide_url
The wrapped VS Code Web on that computer, the URL its proxy announces (see below).
ssh_host, ssh_user, ssh_port
Where Gateway connects. Without ssh_host the Gateway target is unavailable. The port defaults to 22.
jetbrains_ide_path
An IDE backend already installed on the computer. Without it, Gateway asks which IDE to use.
os
macos, linux or windows.

With EMBER_IDE_COMPUTERS unset there is one computer, local, whose ide_url is EMBER_IDE_URL. server_url defaults to EMBER_PUBLIC_URL. Moving these targets onto the registered computers of Computers and the hub is an open item in the server code.

VS Code Web Partial

The VS Code choice is VS Code Web served on the computer itself and wrapped by Ember's proxy (web/proxy/). The proxy adds a title bar and a touch layout for narrow windows on top of an unmodified VS Code build; on a wide window you see stock VS Code. There are two runtimes:

OSE (default)VSC
BuildCode-OSS 1.139.1 compiled by DarkPyonix from the MIT sourceYour own installation of Microsoft's VS Code (code serve-web)
ExtensionsOpen VSXMicrosoft Marketplace
LicenceMITMicrosoft's licence, your responsibility

OSE is the default because Microsoft's server licence forbids hosting or redistributing it. Ember therefore never downloads or bundles Microsoft's server; VSC only runs the copy you installed yourself. OSE is built by the repository's CI for linux-x64, linux-arm64, darwin-arm64 and darwin-x64. As of 2026-10-03 no OSE release has been published yet, so today you either use --runtime vsc or point DPX_OSE_SERVER at an OSE build you have.

On each computer, start the runtime and the proxy with one command from web/proxy. It needs at least one --root: a folder outside every root is refused with 403.

The url in the ready line is the ide_url for that computer. --runtime vsc --check prints whether code is installed and its version, without starting anything. Settings and extensions live in ~/.ember/vscode-web/<runtime>, one folder per runtime, so the two marketplaces never mix.

Roots are not a sandbox

--root limits which folder a URL may open. The extension host and the terminal still run as the operating-system user who started the proxy, and anyone who can log in to the proxy sees that user's files.

JetBrains Gateway Partial

For a JetBrains IDE, Ember builds a Gateway link for an SSH connection and hands it to your operating system, which starts JetBrains Gateway on the machine you are using. Gateway then connects to the computer and opens the session's folder.

You need Gateway installed where the client runs, and SSH access to the computer. JetBrains is moving Gateway into the Toolbox App with a jetbrains:// scheme and only limited compatibility for these links, which is why the client also accepts jetbrains://.

Ember's own editor Planned

The Ember IDE is the reason the client is built on dioxus-compose. It rebuilds the Code-OSS workbench natively in Rust, draws it with Code-OSS's own CSS, and replaces Monaco with a native code editor widget. There is no webview and no JavaScript engine in that window.

Extensions keep running unmodified in the official Node extension host that the OSE server on the computer starts. Ember never reimplements that host; instead it speaks Code-OSS's own connection protocols to it. Those protocols are internal to VS Code, so Ember pins one Code-OSS commit (the one OSE is built from, 1.139.1) and checks the server's version when it connects. The first features are diagnostics, CodeLens and hover, then inline completions.

The connection layer (ember-editor-conn) and the session layer (ember-editor) exist as first code, written but not yet compiled. Until the editor works end to end, choosing Ember IDE shows a placeholder. Track it in #32.

Tab detach Partial

In VS Code Web you can drag an editor tab out of its tab strip to open it in a new IDE window on the same workspace, at the same cursor position.

  • Drop it more than 48 px away from the tab strip, or outside the window, somewhere VS Code does not accept the drop. A short drag still reorders tabs; a gesture never does both.
  • Tabs with unsaved changes are not detached, because the new window reads the file from disk. A message asks you to save first.
  • Alt-drag, multi-selected tabs and editors without a file (Settings, untitled) are left to VS Code.

In a plain browser the new window is a browser window opened at the file and cursor; the selection and scroll position do not carry over. If the browser blocks the popup, a toast offers an Open button. A native IDE window that receives the full state (cursor, selection, scroll) through the ember-bridge message is designed, but no native webview window exists yet. Touch screens are not supported, because VS Code's tab drag uses HTML5 drag and drop, which phones do not produce. Set DPX_TAB_DETACH=0 on the proxy to turn the feature off. Track it in #30.

Phones and tablets Planned

The proxy's touch layout works in a phone or tablet browser today. Extension panels (webviews) need a secure context, though: over plain HTTP to a LAN address they are blank. localhost on the computer itself works. Secure connections from other devices are expected to come with Ember's peer-to-peer transport (#10).

Opening a project on Android or iOS with no Node on the device, through the computer's own VS Code server or an offline working copy, is designed but not built.
