Overview

One AI, many computers

Ember is a development environment for coding agents. Claude Code, Codex, Antigravity and OMP run on one main server that keeps every conversation. Their tools act on whichever of your computers the work needs, and a conversation can move to another computer halfway through.

An early project

Ember has no releases yet, so you build it from source (see Install). This guide describes the code on the develop branch as of 2026-10-03. Each feature that is not finished carries a status (Implemented Partial Planned) and the issue that tracks it.

Conversation first

The main screen lists your projects. Each project shows its conversation sessions with a status: running, waiting for approval, finished or failed. Your computers are listed below the projects, with whether each one is online.

You open a conversation to steer an agent. You send messages, answer its approval requests, interrupt a turn, or move the session to another computer. An IDE is something a conversation opens when you need to read code, not the centre of the app. The reason is simple: agentic work is mostly watching and steering agents, not typing into an editor.

One main server

The main server is a machine you leave running, such as a Mac mini or a Raspberry Pi. It runs ember-server. Every agent CLI runs there, headless and unmodified, as its vendor ships it. Every transcript and every account lives there too.

This is why a conversation is no longer tied to the computer that started it. Close the client and the session keeps running on the main server. Open a client later, on the same computer or another one, and the conversation is where you left it.

Computers, and moving between them

A computer is any machine that holds project files and runs builds. Each one runs ember-node, a small daemon that carries out tool actions for the sessions using it: file reads and writes, searches, commands, terminals and browser traffic. It runs no agent and stores no transcript. The main server is always available as a computer too; it is called local in the API and "The main server" in the client.

A session belongs to a project, and its current computer is an attribute that can change. After a switch, the next tool call runs on the new computer. With your next message the agent is told that the computer changed and that earlier file contents and command output must be read again, because they describe the old machine.

  1. Your message reaches the session on the main server.
  2. The agent CLI decides to read a file or run a command.
  3. Ember sends that action to the session's current computer, where ember-node performs it and streams the result back. The agent sees it as if it had run locally.
  4. The event is stored and pushed to every client that has the session open.

Agents talking to agents

Sessions can message each other directly, whatever the vendor, computer or account. Every agent gets a small CLI, ember-a2a, with a token for its own session. A delivered message enters the target session the way a user message does, with a header naming the sender and a reference to reply to. Rate limits per session and per pair stop two agents from answering each other forever.

You can bring another session into a conversation yourself: type @@ and its title or id in the composer. A leader session can also start teammate sessions that share a task list and a mailbox. The Agents page covers both.

How the pieces connect

The client talks to ember-server over HTTP. ember-server reaches each computer either over HTTP or over a peer-to-peer transport built on iroh (QUIC, with hole punching and a relay fallback). The darkpyonix.dev hub lets a computer join your GitHub account with a one-time code, so you do not type addresses or open ports. Computers and the hub shows each way.
