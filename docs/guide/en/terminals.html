Persistent terminals

Persistent terminals

Start a build in a terminal, close the window, and the build keeps running. Open the IDE later on another computer or a phone, and the same terminal is there with its scrollback and its running program. This page explains how that works and how to use it.

Where this stands

Partial The ember node side and the VS Code Web side are implemented, with tests in crates/node/tests/terms.rs and the companion extension's own tests. The end-to-end checks (a real window closed, the terminal reopened on a second device) have not been run yet. The Ember editor's terminal panel and a terminal list in the Ember client are planned. Track it in #26.

Who owns a terminal

The terminal process belongs to ember node on the computer where it runs, not to the IDE window, not to VS Code's own terminal host and not to the client. Windows, agents and people are clients that attach to it and detach from it. Attaching and detaching never start or stop the program; it runs until it exits or someone kills it.

This is why one terminal can be seen from VS Code Web and, later, from the Ember editor at the same time. VS Code's own persistent terminals are not relied on, because a VS Code server restart or its revive timeout ends them.

Each terminal records its origin (ide-vscode, ide-ember, agent or user), its project, a title and tags, so lists can show where a terminal came from.

What it survives

EventWhat happens to the terminal
The window closes or reloadsNothing. The window only detaches.
You open the IDE on another deviceThe terminal is listed again, with its scrollback and screen.
The VS Code server or ember server restartsNothing. Both are only clients.
ember node restartsBest effort: the program survives through a small PTY keeper process, and the restarted node adopts it again.

The keeper holds a copy of the terminal's handle in its own process session, so the shell is not hung up when node exits. Some limits follow from that design:

  • After a graceful stop, the scrollback and screen carry over. After a crash, the adopted terminal starts with an empty screen until the program draws again.
  • While no node is running, nobody reads the terminal. The program runs until the kernel's buffer is full, then waits. Output in that buffer is not lost.
  • An adopted program's exit status is unknown.
  • A service manager must not kill the keepers along with the daemon: use KillMode=process for systemd and AbandonProcessGroup=true for launchd. The repository does not ship these unit files yet.
  • Windows has no keeper, because node's terminal code is Unix-only.
  • EMBER_NODE_KEEP_PTY=0 turns keepers off; terminals then end with the daemon.

In VS Code Web

VS Code Web reaches persistent terminals through a small web extension, the Ember persistent terminals companion in web/proxy/companion/. It runs in the browser's extension host and talks to node through the proxy, so the node's token never reaches the browser. No VS Code source is patched.

  1. Copy web/proxy/companion/ into the VS Code server's extensions folder as darkpyonix.ember-terminals-0.1.0/. For dpx.serve that is the extensions folder under ~/.ember/vscode-web/<runtime>.
  2. Open a terminal with the profile Ember (persistent).
  3. To make it the default for new terminals and tasks, run Ember: Use Persistent Terminals for New Terminals and Tasks from the command palette. It writes the settings below.

When a window starts, gains focus, and every 5 seconds while it has focus, the companion lists the project's terminals and shows the ones the window does not have yet: running VS Code terminals from any device, and tasks that finished in the last 10 minutes, with their output.

  • Closing a terminal tab yourself (the trash icon) kills the program. The setting ember.terminals.killOnClose controls this.
  • Closing or reloading the window only detaches.
  • Other commands: Ember: Attach to a Persistent Terminal… (every terminal on the computer, any origin), New Persistent Terminal, Take Control of Terminal, Release Control of Terminal, Kill Persistent Terminal.

Tasks from tasks.json run in persistent terminals through ember-term. When the window closes, VS Code eventually disposes the task's terminal; ember-term then detaches and the build keeps running. VS Code's own task state (problem matchers, "task is running") does not carry over to a re-shown terminal.

From any shell: ember-term

ember-term is a small binary built with ember node. It attaches the terminal it runs in to a node session, which also makes it usable as a plain terminal profile.

It finds the node through EMBER_NODE_URL and EMBER_NODE_TOKEN, or through ~/.ember/node/local.json. It forwards its whole environment, and it detaches on SIGHUP instead of ending the program.

Who is in control

Several devices can attach to one terminal at once. By default everyone may type.

  • Typing. Keystrokes from every attached client reach the program in the order node receives them, so when two devices type in turn, neither input is lost.
  • Taking control. Any client can take control. Everyone else becomes read-only and sees a "controlled by <device>" banner; their input is refused, not queued. Control ends when the controller releases it or detaches.
  • Size. The terminal follows the controller's size. With no controller, it follows the client that typed or focused most recently. A passive attach, such as a window restoring its terminal list, never resizes it.
  • Different screen sizes. Other clients draw the terminal at its real size. VS Code cannot scale an extension terminal, so a smaller VS Code window shows wrapped lines instead; the Ember editor is meant to scale to fit.
  • Slow clients. A client that falls far behind is dropped and re-attaches for a fresh screen. It never slows the program or the other clients.

Scrollback and finished terminals

Node keeps a terminal model fed with every byte. Attaching sends a snapshot first (the scrollback, the screen, the cursor and the input modes, including a running full-screen program), then the live stream, with no gap and no overlap between the two.

  • Scrollback keeps 10,000 lines, capped at 3 MB per terminal.
  • A few details are not in the snapshot (scroll region, saved cursor, character sets, tab stops, hyperlinks). A full-screen program repaints them on its next full redraw, and any resize causes one.
  • A finished terminal stays listed (the 100 most recent). The 20 most recent keep their screen, so attaching to a finished task shows its output and then its exit status.

Debugging

A program started under the debugger normally dies with the debug adapter when the window closes. The companion avoids that for two cases by rewriting a launch that uses "console": "integratedTerminal": the program runs in a persistent terminal with the debugger listening on 127.0.0.1, and VS Code attaches to it.

  • Node (node, pwa-node, runtime node), through --inspect-brk.
  • Python (debugpy), through debugpy.listen. debugpy must be importable by that interpreter, or ember.debug.debugpyPath names the folder that contains it.

A window opened later offers "Re-attach the debugger" for the project's running debuggees, or you run Ember: Re-attach Debugger to a Running Debuggee…. Other debug adapters and consoles are left unchanged and are not persistent. Opt out per configuration with "emberPersistent": false, or globally with ember.debug.persistent. This path has not been run against a real VS Code, js-debug or debugpy yet.

For client authors

Every client uses the same node API, authenticated with the node token. Through the proxy the same routes are under /__terms and use the proxy's session cookie instead.

RouteWhat it does
POST /v1/termsCreate a session. A key makes it attach-or-create.
GET /v1/terms?project=&origin=&running=List sessions, oldest first.
GET /v1/terms/{id}/snapshotThe current screen, without attaching.
GET /v1/terms/{id}/attachWebSocket: a hello, then input in and events out.
POST /v1/terms/{id}/controlTake or release control.
POST /v1/terms/{id}/killSIGHUP, then SIGKILL after 3 seconds.

Rust clients use NodeClient::term_create, term_attach and the other term_* methods of ember-node.
