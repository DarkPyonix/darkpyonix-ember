IDE 열기

IDE 열기

대화는 에이전트와 함께 일하는 곳입니다. 코드를 직접 읽거나 고치고 싶을 때는 대화 화면 오른쪽 위의 Open IDE 버튼이 세션의 프로젝트를 IDE로 엽니다. 선택지는 세 가지이고, 하나의 겉모습만 바꾼 것이 아니라 서로 다른 세 프로그램입니다.

현재 상태

VS Code Web과 JetBrains Gateway는 지금 열립니다. 대상 컴퓨터는 서버 설정에 적어 둔 목록에서 가져옵니다. Ember 자체 에디터는 계획 단계이고 (#32), 선택하면 자리 표시 화면만 나옵니다. IDE는 아직 세션의 현재 컴퓨터를 스스로 따라가지 않습니다. 어느 컴퓨터가 열리는가를 보십시오.

세 가지 선택지

선택지열리는 것상태
Ember IDEdioxus-compose가 네이티브로 그리는 Ember 자체 에디터입니다. 웹뷰도 JavaScript 엔진도 없습니다.계획 #32
VS Code컴퓨터에서 도는 VS Code Web을 Ember의 프록시로 감싼 것입니다. 기본 브라우저에서 열립니다.부분
JetBrains Gatewayjetbrains-gateway:// 링크입니다. 지금 쓰는 기기에 설치된 Gateway를 띄우고, SSH로 컴퓨터에 접속합니다.부분

VS Code와 Gateway가 부분인 이유는 같습니다. 열리기는 하지만, 어느 컴퓨터에서 열지는 세션이 아니라 설정 목록에서 정해집니다. Gateway는 아직 실제 Gateway 설치본으로 돌려 보지 않았고, 만들어지는 링크만 테스트합니다.

버튼이 하는 일

클라이언트는 이 세션에서 각 IDE를 어떻게 여는지 메인 서버에 묻습니다. 서버는 데이터만 돌려주고 창을 직접 열지 않습니다. 런처 프로세스는 웹뷰를 절대 만들면 안 되기 때문입니다.

응답에는 대상 셋이 항상 ember, vscode, gateway 순서로 들어 있습니다. 각 대상에는 available 이 있고, 쓸 수 없을 때는 reason 이 붙습니다(예: "no ide_url configured for computer"). 클라이언트는 조용히 실패하지 않고 이 이유를 보여 줍니다.

  • 클라이언트는 마지막으로 고른 대상을 기억했다가 다음에 맨 앞에 보여 줍니다.
  • URL은 대상에 맞는 스킴일 때만 운영체제에 넘깁니다. VS Code는 http 나 https, Gateway는 jetbrains-gateway:// 나 jetbrains:// 입니다. 그래서 서버 응답이 클라이언트에게 로컬 파일이나 프로그램을 열게 할 수 없습니다.
  • 열리는 폴더는 세션의 작업 디렉터리이고, 그 컴퓨터의 경로로 해석합니다.

REST 경로에는 버전이 없어서 모두 /api/ 로 시작합니다.

어느 컴퓨터가 열리는가 부분

세션에는 이미 현재 컴퓨터가 있지만, IDE 대상은 아직 그것을 읽지 않습니다. 그때까지 서버는 각 컴퓨터의 IDE 정보를 EMBER_IDE_COMPUTERS 에서 가져오고, 요청이 ?computer= 로 다른 컴퓨터를 지정하지 않으면 기본 컴퓨터를 엽니다. 값은 인라인 JSON이거나 JSON 파일 경로입니다.

ide_url
그 컴퓨터에서 감싼 VS Code Web, 즉 프록시가 알려 주는 URL입니다(아래 참고).
ssh_host, ssh_user, ssh_port
Gateway가 접속할 곳입니다. ssh_host 가 없으면 Gateway 대상은 쓸 수 없습니다. 포트 기본값은 22입니다.
jetbrains_ide_path
컴퓨터에 이미 설치된 IDE 백엔드입니다. 없으면 Gateway가 어떤 IDE를 쓸지 묻습니다.
os
macos, linux, windows 중 하나입니다.

EMBER_IDE_COMPUTERS 가 없으면 컴퓨터는 local 하나이고, 그 ide_url 은 EMBER_IDE_URL 입니다. server_url 의 기본값은 EMBER_PUBLIC_URL 이고, 없으면 요청이 들어온 호스트입니다. 이 대상을 컴퓨터와 허브 에서 등록한 컴퓨터로 옮기는 일은 서버 코드에 남은 과제입니다.

VS Code Web 부분

VS Code 선택지는 컴퓨터 자체에서 서비스하는 VS Code Web을 Ember의 프록시 (ember/proxy/)로 감싼 것입니다. 프록시는 수정하지 않은 VS Code 빌드 위에, 좁은 창을 위한 타이틀 바와 터치 레이아웃을 더합니다. 넓은 창에서는 순정 VS Code가 보입니다. 런타임은 두 가지입니다.

OSE (기본값)VSC
빌드DarkPyonix가 MIT 소스로 컴파일한 Code-OSS 1.139.1사용자가 직접 설치한 Microsoft VS Code (code serve-web)
확장Open VSXMicrosoft Marketplace
라이선스MITMicrosoft 라이선스, 사용자 책임

OSE가 기본값인 이유는 Microsoft 서버 라이선스가 호스팅과 재배포를 금지하기 때문입니다. 그래서 Ember는 Microsoft 서버를 내려받거나 함께 묶지 않고, VSC는 사용자가 직접 설치한 사본만 실행합니다. OSE는 저장소 CI가 linux-x64, linux-arm64, darwin-arm64, darwin-x64용으로 빌드합니다. 2026-10-03 현재 공개된 OSE 릴리스는 아직 없습니다. 그래서 지금은 --runtime vsc 를 쓰거나, 가지고 있는 OSE 빌드를 DPX_OSE_SERVER 로 지정합니다.

각 컴퓨터에서 ember/proxy 로 가서 명령 하나로 런타임과 프록시를 띄웁니다. --root (또는 DPX_FOLDER_ROOTS) 가 적어도 하나 필요하고, 어느 루트에도 속하지 않는 폴더는 403으로 거절합니다.

ready 줄의 url 이 그 컴퓨터의 ide_url 입니다. --runtime vsc --check 는 아무것도 띄우지 않고 code 설치 여부와 버전만 출력합니다. 설정과 확장은 ~/.ember/vscode-web/<runtime> 에 런타임마다 따로 두므로, 두 마켓플레이스가 섞이지 않습니다.

루트는 샌드박스가 아닙니다

--root 는 URL이 열 수 있는 폴더만 제한합니다. 확장 호스트와 터미널은 여전히 프록시를 띄운 운영체제 사용자로 실행되고, 프록시에 로그인할 수 있는 사람은 그 사용자의 파일을 볼 수 있습니다.

JetBrains Gateway 부분

JetBrains IDE를 고르면 Ember가 SSH 접속용 Gateway 링크를 만들어 운영체제에 넘기고, 운영체제가 지금 쓰는 기기에서 JetBrains Gateway를 띄웁니다. 그다음 Gateway가 컴퓨터에 접속해 세션의 폴더를 엽니다.

클라이언트가 도는 곳에 Gateway가 설치되어 있어야 하고, 컴퓨터에 SSH로 접속할 수 있어야 합니다. JetBrains는 Gateway를 Toolbox App으로 옮기면서 jetbrains:// 스킴을 쓰고, 이 링크와의 호환은 제한적으로만 유지합니다. 그래서 클라이언트는 jetbrains:// 도 받아들입니다.

Ember 자체 에디터 계획

클라이언트를 dioxus-compose로 만드는 이유가 바로 Ember IDE입니다. Code-OSS 워크벤치를 Rust로 네이티브하게 다시 만들고, Code-OSS의 CSS로 그리며, Monaco 대신 네이티브 코드 에디터 위젯을 씁니다. 이 창에는 웹뷰도 JavaScript 엔진도 없습니다.

확장은 컴퓨터의 OSE 서버가 띄운 공식 Node 확장 호스트에서 수정 없이 그대로 돕니다. Ember는 그 호스트를 다시 구현하지 않고, Code-OSS 자체의 연결 프로토콜로 대화합니다. 이 프로토콜은 VS Code 내부용이라서 Ember는 Code-OSS 커밋 하나(OSE가 빌드되는 1.139.1)에 고정하고, 접속할 때 서버 버전을 확인합니다. 첫 기능은 진단, CodeLens, 호버이고, 그다음이 인라인 완성입니다.

연결 계층(ember-editor-conn)과 세션 계층(ember-editor)은 첫 코드가 있습니다. CI에서 빌드되고 테스트를 통과하지만, 실제 OSE 서버를 상대로 하는 종단 간 테스트는 직접 켜야 하며 CI에는 들어 있지 않습니다. 에디터가 처음부터 끝까지 동작하기 전까지 Ember IDE를 고르면 자리 표시 화면이 나옵니다. 진행은 #32 에서 확인합니다.

탭 분리 부분

VS Code Web에서 에디터 탭을 탭 줄 밖으로 끌어내면, 같은 워크스페이스의 새 IDE 창에서 같은 커서 위치로 열립니다.

  • 탭 줄에서 48 px 넘게 떨어진 곳이나 창 밖, 즉 VS Code가 드롭을 받지 않는 곳에 놓습니다. 짧게 끌면 여전히 탭 순서만 바뀌고, 한 동작이 두 가지를 함께 하지는 않습니다.
  • 저장하지 않은 변경이 있는 탭은 분리하지 않습니다. 새 창은 디스크의 파일을 읽기 때문입니다. 먼저 저장하라는 메시지가 뜹니다.
  • Alt 드래그, 여러 개를 고른 탭, 파일이 없는 에디터(설정, 제목 없음)는 VS Code에 맡깁니다.

일반 브라우저에서는 새 창이 그 파일과 커서 위치로 열린 브라우저 창입니다. 선택 영역과 스크롤 위치는 넘어가지 않습니다. 브라우저가 팝업을 막으면 Open 버튼이 있는 알림이 뜹니다. 전체 상태(커서, 선택 영역, 스크롤)를 ember-bridge 메시지로 받는 네이티브 IDE 창은 설계되어 있지만, 네이티브 웹뷰 창은 아직 없습니다. VS Code의 탭 드래그는 HTML5 드래그 앤 드롭이고 휴대폰은 이것을 만들지 않으므로, 터치 화면은 지원하지 않습니다. 프록시에서 DPX_TAB_DETACH=0 으로 이 기능을 끕니다. 진행은 #30 에서 확인합니다.

휴대폰과 태블릿 계획

프록시의 터치 레이아웃은 지금도 휴대폰과 태블릿 브라우저에서 동작합니다. 다만 확장 패널(웹뷰)은 보안 컨텍스트가 필요해서, LAN 주소로 일반 HTTP 접속을 하면 빈 화면이 됩니다. 컴퓨터 자신의 localhost 에서는 동작합니다. 다른 기기에서의 보안 연결은 Ember의 P2P 전송 계층과 함께 들어올 예정입니다 (#10).

기기에 Node가 없는 Android와 iOS에서, 컴퓨터 자신의 VS Code 서버나 오프라인 작업 사본으로 프로젝트를 여는 방식은 설계만 되어 있고 만들지 않았습니다.
