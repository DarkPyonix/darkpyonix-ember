영구 터미널

영구 터미널

터미널에서 빌드를 시작하고 창을 닫아도 빌드는 계속 돕니다. 나중에 다른 컴퓨터나 휴대폰에서 IDE를 열면, 같은 터미널이 스크롤백과 실행 중인 프로그램을 그대로 가진 채 보입니다. 이 페이지는 그 동작 방식과 사용법을 설명합니다.

현재 상태

부분 ember node 쪽과 VS Code Web 쪽은 구현되어 있고, ember/node/tests/terms.rs 와 컴패니언 확장 자체의 테스트가 있습니다. 실제 창을 닫고 두 번째 기기에서 터미널을 다시 여는 종단 간 확인은 아직 하지 않았습니다. Ember 에디터의 터미널 패널과 Ember 클라이언트의 터미널 목록은 계획 단계입니다. 진행은 #26 에서 확인합니다.

터미널의 주인

터미널 프로세스는 그것이 도는 컴퓨터의 ember node 가 소유합니다. IDE 창도, VS Code 자체의 터미널 호스트도, 클라이언트도 아닙니다. 창, 에이전트, 사람은 모두 터미널에 붙었다 떨어지는 클라이언트입니다. 붙고 떨어지는 일은 프로그램을 시작하거나 멈추지 않고, 프로그램은 스스로 끝나거나 누군가 죽일 때까지 돕니다.

그래서 한 터미널을 VS Code Web과, 나중에는 Ember 에디터에서 동시에 볼 수 있습니다. VS Code 자체의 영구 터미널에는 기대지 않습니다. VS Code 서버가 재시작하거나 되살리기 제한 시간이 지나면 끝나기 때문입니다.

터미널마다 출처(ide-vscode, ide-ember, agent, user), 프로젝트, 제목, 태그를 기록합니다. 그래서 목록에서 터미널이 어디서 왔는지 보여 줄 수 있습니다.

무엇을 견디는가

일어난 일터미널에 생기는 일
창을 닫거나 새로 고침아무 일도 없습니다. 창은 떨어지기만 합니다.
다른 기기에서 IDE를 엶터미널이 스크롤백, 화면과 함께 다시 목록에 나옵니다.
VS Code 서버나 ember server 재시작아무 일도 없습니다. 둘 다 클라이언트일 뿐입니다.
ember node 재시작최선을 다합니다. 프로그램은 작은 PTY 키퍼 프로세스 덕에 살아남고, 재시작한 node가 다시 넘겨받습니다.

키퍼는 자기 프로세스 세션에서 터미널 핸들의 사본을 쥐고 있으므로, node가 끝나도 셸이 끊기지 않습니다. 이 설계에서 몇 가지 한계가 따라옵니다.

  • 정상 종료 뒤에는 스크롤백과 화면이 이어집니다. 충돌 뒤에는 넘겨받은 터미널이 빈 화면으로 시작하고, 프로그램이 다시 그리면 채워집니다.
  • node가 없는 동안에는 아무도 터미널을 읽지 않습니다. 프로그램은 커널 버퍼가 찰 때까지 돌다가 기다립니다. 그 버퍼의 출력은 사라지지 않습니다.
  • 넘겨받은 프로그램의 종료 상태는 알 수 없습니다.
  • 서비스 관리자가 데몬과 함께 키퍼를 죽이면 안 됩니다. systemd는 KillMode=process, launchd는 AbandonProcessGroup=true 를 씁니다. 저장소에는 아직 이 유닛 파일이 없습니다.
  • node의 터미널 코드는 Unix 전용이라서 Windows에는 키퍼가 없습니다.
  • EMBER_NODE_KEEP_PTY=0 은 키퍼를 끕니다. 그러면 터미널은 데몬과 함께 끝납니다.

VS Code Web에서

VS Code Web은 작은 웹 확장인 Ember persistent terminals 컴패니언 (ember/proxy/companion/)으로 영구 터미널에 닿습니다. 이 확장은 브라우저의 확장 호스트에서 돌고 프록시를 거쳐 node와 대화하므로, node 토큰은 브라우저에 가지 않습니다. VS Code 소스는 고치지 않습니다.

  1. ember/proxy/companion/ 을 VS Code 서버의 확장 폴더에 darkpyonix.ember-terminals-0.1.0/ 이라는 이름으로 복사합니다. dpx.serve 라면 ~/.ember/vscode-web/<runtime> 아래의 extensions 폴더입니다.
  2. Ember (persistent) 프로필로 터미널을 엽니다.
  3. 새 터미널과 작업의 기본값으로 삼으려면 명령 팔레트에서 Ember: Use Persistent Terminals for New Terminals and Tasks 를 실행합니다. 이 명령은 기본 프로필을 바꾸고, 컴퓨터에 있는 ember-term 경로를 입력하면 작업용 자동화 프로필도 설정합니다. 아래 마지막 설정은 이 명령이 써 주지 않으므로 직접 추가합니다.

창이 시작될 때, 포커스를 얻을 때, 그리고 포커스가 있는 동안 5초마다 컴패니언은 프로젝트의 터미널을 조회하고 창에 아직 없는 것을 보여 줍니다. 어느 기기에서 열었든 실행 중인 VS Code 터미널과, 최근 10분 안에 끝난 작업이 출력과 함께 나옵니다.

  • 터미널 탭을 직접 닫으면(휴지통 아이콘) 프로그램을 죽입니다. ember.terminals.killOnClose 설정이 이것을 정합니다.
  • 창을 닫거나 새로 고치면 떨어지기만 합니다.
  • 다른 명령: Ember: Attach to a Persistent Terminal…(출처와 상관없이 컴퓨터의 모든 터미널), New Persistent Terminal, Take Control of Terminal, Release Control of Terminal, Kill Persistent Terminal.

tasks.json 의 작업은 ember-term 을 거쳐 영구 터미널에서 돕니다. 창이 닫히면 VS Code가 언젠가 작업 터미널을 정리하고, 그때 ember-term 은 떨어지기만 하므로 빌드는 계속 돕니다. VS Code 자체의 작업 상태(문제 매처, "작업 실행 중")는 다시 보인 터미널로 이어지지 않습니다.

어느 셸에서나: ember-term

ember-term 은 ember node와 함께 빌드되는 작은 바이너리입니다. 자신이 도는 터미널을 node 세션에 붙이므로, 일반 터미널 프로필로도 쓸 수 있습니다.

node는 EMBER_NODE_URL 과 EMBER_NODE_TOKEN, 또는 ~/.ember/node/local.json 으로 찾습니다. 자신의 환경 변수를 모두 넘기고, SIGHUP을 받으면 프로그램을 끝내지 않고 떨어지기만 합니다.

누가 제어하는가

한 터미널에 여러 기기가 동시에 붙을 수 있습니다. 기본적으로는 모두 입력할 수 있습니다.

  • 입력. 붙어 있는 모든 클라이언트의 키 입력은 node가 받은 순서대로 프로그램에 들어갑니다. 그래서 두 기기가 번갈아 입력해도 어느 쪽 입력도 사라지지 않습니다.
  • 제어권 가져오기. 어느 클라이언트든 제어권을 가져올 수 있습니다. 나머지는 모두 읽기 전용이 되고 "controlled by <device>" 배너를 봅니다. 그들의 입력은 쌓이지 않고 거절됩니다. 제어권은 제어하는 쪽이 놓거나 떨어지면 끝납니다.
  • 크기. 터미널은 제어하는 쪽의 크기를 따릅니다. 제어하는 쪽이 없으면 가장 최근에 입력하거나 포커스를 준 클라이언트를 따릅니다. 창이 터미널 목록을 되살리는 것 같은 수동 붙기는 크기를 바꾸지 않습니다.
  • 화면 크기가 다를 때. 다른 클라이언트는 터미널을 실제 크기로 그립니다. VS Code는 확장 터미널을 축소하지 못하므로 더 작은 VS Code 창에서는 줄이 꺾여 보입니다. Ember 에디터는 화면에 맞게 축소하도록 설계되어 있습니다.
  • 느린 클라이언트. 한참 뒤처진 클라이언트는 끊기고, 다시 붙어 새 화면을 받습니다. 프로그램이나 다른 클라이언트를 느리게 하지 않습니다.

스크롤백과 끝난 터미널

node는 모든 바이트를 받는 터미널 모델을 유지합니다. 붙으면 먼저 스냅샷(스크롤백, 화면, 커서, 입력 모드, 실행 중인 전체 화면 프로그램 포함)을 보내고, 이어서 실시간 스트림을 보냅니다. 둘 사이에는 빈틈도 겹침도 없습니다.

  • 스크롤백은 10,000줄까지, 터미널마다 3 MB 상한으로 보관합니다.
  • 스냅샷에 들어가지 않는 세부 사항이 몇 가지 있습니다(스크롤 영역, 저장된 커서, 문자 집합, 탭 위치, 하이퍼링크). 전체 화면 프로그램은 다음 전체 다시 그리기 때 이것을 다시 그리고, 크기를 바꾸면 언제나 다시 그립니다.
  • 끝난 터미널은 목록에 남습니다(최근 100개). 최근 20개는 화면을 보관하므로, 끝난 작업에 붙으면 출력과 종료 상태를 볼 수 있습니다.

디버깅

디버거로 시작한 프로그램은 보통 창이 닫힐 때 디버그 어댑터와 함께 죽습니다. 컴패니언은 "console": "integratedTerminal" 을 쓰는 launch 를 바꿔 써서, 두 경우에 이를 막습니다. 프로그램은 127.0.0.1에서 디버거가 기다리는 영구 터미널에서 돌고, VS Code는 거기에 attach합니다.

  • Node(node, pwa-node, 런타임 node): --inspect-brk 로.
  • Python(debugpy): debugpy.listen 으로. 그 인터프리터가 debugpy를 import할 수 있어야 하고, 아니면 ember.debug.debugpyPath 에 debugpy가 든 폴더를 적습니다.

나중에 연 창은 프로젝트에서 실행 중인 디버기에 대해 "디버거 다시 붙이기"를 제안합니다. Ember: Re-attach Debugger to a Running Debuggee… 로 직접 실행할 수도 있습니다. 다른 디버그 어댑터와 콘솔은 그대로 두며 영구적이지 않습니다. 구성마다 "emberPersistent": false 로, 전체는 ember.debug.persistent 로 끕니다. 이 경로는 아직 실제 VS Code, js-debug, debugpy로 돌려 보지 않았습니다.

클라이언트 개발자용

모든 클라이언트는 node 토큰으로 인증하는 같은 node API를 씁니다. 프록시를 거치면 같은 경로가 /__terms 아래에 있고, 대신 프록시의 세션 쿠키를 씁니다.

경로하는 일
POST /terms세션을 만듭니다. key 를 주면 있으면 붙고 없으면 만듭니다.
GET /terms?project=&origin=&running=세션 목록, 오래된 것부터.
GET /terms/{id}/snapshot붙지 않고 현재 화면만 가져옵니다.
GET /terms/{id}/attachWebSocket: hello를 보낸 뒤 입력을 보내고 이벤트를 받습니다.
POST /terms/{id}/control제어권을 가져오거나 놓습니다.
POST /terms/{id}/killSIGHUP, 3초 뒤 SIGKILL.

Rust 클라이언트는 ember-node 의 NodeClient::term_create, term_attach 와 다른 term_* 메서드를 씁니다.

아직 없는 것

  • 같은 세션에 붙는 Ember 에디터의 터미널 패널 (#32).
  • Ember 클라이언트의 컴퓨터별, 프로젝트별 터미널 목록(출처 표시와 종료 포함) (#26).
  • 메인 서버를 통해서만 컴퓨터에 닿는 클라이언트를 위해 ember server가 붙기를 중계하는 기능.
  • 측정: 다시 붙기 500 ms 목표와 유휴 터미널당 2 MB는 추정치이고 측정하지 않았습니다.
